## What changed, and what we corrected

Historical Cosign 3.1.2 bundles were invisible to Kyverno because GHCR's fallback
index advertised the wrong descriptor artifactType. The earlier conclusion that
Cosign 3.1.4 only fixed local-save was WRONG: the actual native 3.1.4 fixture has
correct remote bundle descriptors and was admitted. The first final harness
correctly failed its mistaken expected-denial case. Its raw failed output is
retained; native 3.1.4 is a compatible positive, not a negative control.

The selected strict-v1 path uses `cosign attest-blob --statement` on an explicit
in-toto Statement/v1 with SLSA provenance/v1 and the exact image name/digest, then
publishes unchanged bundle bytes with ORAS's explicit bundle artifactType and
referrers-tag layout. This is not a downgrade or unsigned metadata workaround:
Cosign verification still checks the certificate identity AND issuer, Sigstore
trust/transparency material and subject claims. Descriptor, manifest and blob
readbacks bind the signed bytes; strict content checks bind workflow and revision.
The ORAS path remains necessary for publishing our explicit local v1 bundle;
republishing the already-correct native signature/SBOM is redundant but checked.

Two real release failures were not hidden:

1. [44206380255](https://github.com/PontoPe/ProvenancePipeline/actions/runs/44206380255) failed the unchanged CRITICAL scan on the old Go 1.26.5 builder. The official Go 1.26.11-alpine index was resolved and digest-pinned; the next scan passed.
2. [44207607809](https://github.com/PontoPe/ProvenancePipeline/actions/runs/44207607809) passed layout/crypto but failed the strict Statement/v1 content gate: native image `attest` emits Statement/v0.1 even with a SLSA v1 predicate. We changed the publisher, not the contract. The supported `attest-blob --statement` route signs explicit v1 bytes. Image `attest --statement` accepted the flag but still required a predicate in the tested binary.

The required own publication and separate clean-runner content verification run
before the optional GitHub writer. Workflow concurrency serializes fallback-index
writers per ref. PR jobs cannot publish/sign releases; publication is main-only.

## Cache and outage interpretation

Do not describe all three registry results as cryptographic denials. The warm
and expired-cache probes reached their webhook deadline while the controller
was blocked fetching GHCR; the cold probe returned an explicit denial with
GHCR `connection refused`. Controller logs also preserve fetch cancellation
(`context canceled`). Independent
unsigned requests still reached the webhook and received signature denials during
the fault. Scoped packet counters confirm intercepted GHCR HTTPS traffic.

The bounded cache experiment explicitly used TTL 20s and capacity 1,048,576,
not the default 60m/1,000. At the recently verified probe, rule 2 logged a cache
HIT, but rule 1 disabled caching because it declares a request-evaluated gate,
then attempted the registry. Therefore a warm signature-rule cache did NOT make
the provenance rule available offline. The observed warm request completed
11.386577097931877s after the initial successful verification. After TTL expiry,
and with a freshly restarted controller, refusal remained fail-closed. This does
not claim that the 60-minute default was elapsed or that every possible policy
consults the registry on every admission.

Simply disconnecting Service endpoints was insufficient to terminate existing
apiserver keep-alive connections in an initial attempt. The final webhook fault
used scoped iptables OUTPUT/FORWARD rejects to the actual controller Pod/9443
inside ONLY the disposable node. Registry faults separately rejected GHCR IPv4
HTTPS in that node's FORWARD chain. The recorded execution removed all injected
rules and restored the original deployment args; the restoration patch and
successful rollout are preserved. The final restricted observer separately
read back policy and namespace enforcement, not Deployment args, before lab
destruction. The harness cleanup is not best-effort: an exception while removing
one rule can prevent later cleanup steps. Reuse only in a disposable lab and
verify restoration independently; improve this path before operational reuse.

The earlier graceful scale-to-zero finding remains a limitation: controller
shutdown can deregister webhooks. A network fault with registered webhooks is
not equivalent to privileged administrative removal. No claim of surviving
cluster-admin disabling enforcement is made. Continuous alerting is not deployed.

## Reproduce and recover

1. Verify the documented checksums/signatures; use a dedicated one-node kind
   cluster named `prove-lab-...`, a separate kubeconfig, 4GiB memory/2CPU creation
   limits, loopback API binding. Never reuse an existing cluster by assumption.
2. Install checksum-verified Kyverno1.19.2 into that lab, then the unchanged
   repository policy. Wait for admission readiness AND usable webhook endpoints.
   The historical production bootstrap remains1.18.2; do not confuse it with
   the selected lab installation or deploy it blindly for this experiment.
3. Create `prove-lab`, label `provenancepipeline.io/admission=enforced`, apply
   `tests/integration/observer-rbac.yaml`. Confirm context and exact node identity.
4. On reviewed main, dispatch `release.yml` with `skip_github_writer=true` and
   `publish_negative_fixtures=true`. Require successful exact-head release; obtain
   the `own-publication` artifact through `gh run download RUN -n own-publication`.
5. Run `PATH="$PWD/.lab/bin:$PATH" KUBECONFIG=/path/to/lab-kubeconfig python3 scripts/b5_admission.py --context kind-prove-lab-... --image ghcr.io/pontope/provenancepipeline@sha256:EXACT_DIGEST --fixtures /path/to/artifact/negative-fixtures --out /path/to/fresh-evidence`.
   The real positive Pod is named `own-proof`; reruns must explicitly remove only
   that known lab Pod, or use a fresh lab. All other admission probes are dry-run.
6. Run `scripts/b5_outages.py` with the same context/image and a fresh `--out`.
   It requires permission to exec iptables ONLY inside its explicitly verified
   own kind node. It deliberately alters/removes the lab policy and restarts its
   controller. Never run it on production. If interrupted outside finally,
   remove only rules tagged `prove-lab-b5-*` from that node, restore original
   deployment args and the repository policy, require positive health plus the
   restricted negative checker, then destroy the named lab.
7. Destroy only the named kind cluster and verify all pre-existing Docker
   service IDs/uptimes remain unchanged. Do not prune shared images/volumes.

The observer is one-shot, not a daemon. This run provisions no monitoring stack.
The two harness scripts are review candidates; review their cleanup/timeout and
classification paths before adopting them operationally.

## Portfolio case / blog source

Starting reference: GitHub's [Safeguard your containers with container signing](https://github.blog/security/supply-chain-security/safeguard-container-signing-capability-actions/).
The useful question was not whether signing returned success, but whether the
admission consumer could discover and authenticate the intended evidence after
the optional writer disappeared. Registry descriptors were part of the effective
trust path, even though they were not themselves proof of authenticity.

The July baseline coupled successful admission to GitHub's redundant provenance
writer. A current-version compatibility experiment established two improvements:
native Cosign3.1.4 already corrects remote descriptor metadata, and explicit-v1
statement signing plus deterministic ORAS readback satisfies our stricter content
contract without relying on GitHub's writer. Failures in scanning and statement
format were kept as evidence rather than bypassed. The positive proof was an
actual healthy workload; the negative proof included a signed wrong predicate
and a proof attached to the wrong subject digest.

The outage experiment also changed the availability story: a signature-rule
cache hit does not imply that a provenance rule can operate without the registry.
The final result remains **SLSA Build L2, verified at admission**, not L3 and not
a guarantee against a compromised authorized builder or cluster administrator.
